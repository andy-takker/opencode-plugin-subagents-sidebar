# OpenCode Subagents Sidebar — спецификация

## Цель и согласованный результат

Публичный open-source плагин для OpenCode V2, поддерживаемый как отдельный
Git-репозиторий и распространяемый через GitHub/npm. Справа, аналогично MCP,
показываются субагенты текущего дерева: название задачи, статус, вложенные
субагенты, активные первыми и переход в сессию нажатием.

Исходники располагаются в `~/workspace/my/opencode-plugin-subagents-sidebar`.
Имя проекта и желаемое имя npm-пакета: `opencode-plugin-subagents-sidebar`.
Лицензия: MIT. Основной язык публичной документации — английский.

Эта спецификация заменяет вариант локального плагина из
`~/.config/opencode/plugins/subagents-sidebar/docs/superpowers/specs/`.
Предыдущий план реализации требует обновления под самостоятельный репозиторий.

## Поведение панели

1. Найти корневую сессию открытой сессии. Отобразить всех её потомков
   рекурсивно, исключив корень и чужие деревья.
2. Переход в дочернюю сессию сохраняет список того же дерева. Переход в другой
   корень заменяет список. Возврат восстанавливает дерево из OpenCode.
3. Каждая строка содержит название сессии и текстовый статус с цветом текущей
   темы. Пустое название заменяется идентификатором.
4. Активные строки идут первыми; внутри групп — время создания по возрастанию,
   затем идентификатор. Завершённые сессии остаются в списке.
5. Нажатие строки открывает соответствующую сессию через штатный router.
6. Пустая секция показывает `No subagents`. Загрузка и ошибка имеют отдельные
   состояния; после ошибки доступен повтор загрузки.
7. Длинные Unicode-названия ограничиваются шириной панели; статус читаем
   без различения цветов. Геометрией и видимостью sidebar управляет OpenCode.

## Данные и жизненный цикл

- Использовать публичные TUI API OpenCode и подключённый клиент:
  `@opencode/plugin/tui`, слот `sidebar.content`, session API и router.
- Проверить фактические типы установленной версии до реализации адаптера.
  Начальная проверяемая версия — OpenCode v2.2.5.
- Первичная загрузка включает существующих субагентов. Кеш не считается
  полным деревом: при необходимости читать предков и все страницы потомков
  через публичный API. Лимит списка по умолчанию — 50.
- Использовать реактивный кеш и события, без постоянного периодического опроса.
  Повторное подключение восстанавливает актуальное состояние.
- `Running` имеет приоритет над outcome предыдущего исполнения.
  `Done`, `Error`, `Interrupted` показываются только при подтверждённом
  исходе последнего исполнения; иначе `Idle` или `Unknown`.
- Повторный запуск обновляет существующую строку. Поздние ответы предыдущего
  дерева не изменяют текущее; события во время загрузки не теряются.
- Удалённые сессии не восстанавливаются устаревшим ответом. При выключении
  плагина очищаются подписки и ресурсы; поздние ответы ничего не публикуют.
- Ошибки запросов не маскируются под пустой список. Обход защищён от циклов
  parentID и повторяющихся курсоров; параллелизм запросов ограничен.

## Архитектура и структура репозитория

Один пакет, один TUI entrypoint, без серверной части. Разделить ответственность:

- `src/model.ts`: чистое построение строк, статусы, сортировка.
- `src/controller.ts`: загрузка дерева, обновления, защита от гонок, cleanup.
- `src/opencode-source.ts`: адаптация публичных типов и событий OpenCode.
- `src/tui.tsx`: регистрация секции, Solid-состояние, отображение и навигация.
- Тесты располагаются рядом с соответствующими модулями.
- `docs/`: архитектура, совместимость, процесс релизов и рабочие spec/plan.
- `.github/`: CI, шаблоны issue и pull request, обновление зависимостей.

TypeScript strict. Типы интеграции брать из официального API, а не заменять
неточными локальными декларациями или `any`. Собственная модель отделена от
типов SDK. Комментарии объясняют ограничения и причины решений.

## Пакет и воспроизводимая разработка

- ESM-пакет с публичным экспортом `./tui`, корректными metadata и LICENSE.
  Конкретную форму поставки TSX/сборки определить по поддерживаемому загрузчику
  OpenCode и закрепить в плане до реализации.
- Установленный ранее `@opencode-ai/plugin` V1 не использовать как API V2.
- Зафиксировать версию Bun и lockfile. В CI использовать frozen lockfile.
- Предоставить команды `test`, `typecheck`, `lint`, `format:check`, `check`
  и `package:check`; README содержит точные команды разработки.
- Использовать один согласованный набор lint/format-инструментов без
  дублирующих проверок. Runtime-зависимости минимальны.
- Host-owned библиотеки OpenCode/Solid/OpenTUI не должны создавать вторую
  несовместимую копию runtime. Peer-зависимости и диапазоны подтверждаются
  официальным контрактом загрузчика.
- Явный allowlist файлов npm-пакета: entrypoint и необходимые модули/артефакты,
  README, LICENSE. Исключить тесты, рабочие планы, личные пути, конфигурацию
  пользователя и служебные файлы.
- Проверка tarball должна выявлять отсутствующие файлы, неразрешимые внутренние
  импорты и непреднамеренно опубликованные файлы. Проверить загрузку именно
  упакованного плагина, а не только исходников из checkout.

## Проверки качества и CI

- Unit-тесты модели: вложенность, чужие деревья, порядок, статусы, повторный
  запуск, пустые заголовки, циклы и дубликаты.
- Тесты контроллера: пагинация, восстановление дерева, переключение корня,
  поздние ответы, удаление во время загрузки, ошибки, reconnect и dispose.
- Контрактные тесты адаптера: реальные формы ответов/событий, нормализация
  статусов и передача параметров пагинации.
- TUI-тесты: состояния секции, правильный id для навигации, длинные названия,
  ограниченная ширина и cleanup. Использовать поддерживаемый тестовый рендерер.
- CI на pull request и push в main запускает проверку типов, lint, формат,
  тесты и проверку пакета. Проверки Linux и macOS; поддержку Windows пока
  не заявлять без проверки.
- GitHub Actions используют минимальные permissions и закреплённые версии
  действий; автоматическое обновление зависимостей создаёт проверяемые PR.
- Не подменять реальную runtime-проверку успешными unit-тестами. README
  содержит матрицу фактически проверенных версий и известные ограничения.

## Документация и сопровождение

- README: назначение, пример панели, требования, установка локального пакета
  и npm-версии, использование, обновление, отключение и диагностика.
- До первого опубликованного релиза явно отмечать статус unreleased, чтобы
  инструкция не обещала установку несуществующей npm-версии.
- CONTRIBUTING: установка, команды, архитектура, правила изменений,
  ожидания от тестов и отчётов об ошибках.
- CHANGELOG: пользовательские изменения по версиям, включая совместимость.
- LICENSE (MIT), шаблоны bug report / feature request / pull request,
  SECURITY с реальным способом непубличного сообщения об уязвимости после
  определения GitHub-репозитория. Не выдумывать адреса или контакты.
- Документировать ограничения публичных API и решения, важные для обновления
  OpenCode. Не обещать совместимость с непроверенными будущими версиями.

## Версии и релизы

- SemVer с начальной линией `0.x`; несовместимые изменения до 1.0 повышают
  minor и явно описываются в CHANGELOG. Исправления повышают patch.
- Один источник номера версии — package.json. Тег `vX.Y.Z` должен совпадать
  с версией пакета. Релиз содержит заметки об изменениях и совместимости.
- Перед релизом обязательны все проверки и smoke-проверка пакета в OpenCode.
- Для npm использовать GitHub Actions trusted publishing/OIDC с provenance
  при доступности этого режима для аккаунта; токены не хранить в репозитории.
  Первичную настройку доверия и прав описать как шаг подготовки публикации.
- Создание локального Git-репозитория входит в задачу. GitHub owner/remote
  и доступность npm-имени проверяются перед удалённым созданием и публикацией;
  занятое имя не заменяется молча. Выпуск первой публичной версии выполняется
  отдельным явным действием после проверки готовности пакета.

## Локальное подключение

Разработка ведётся в новом репозитории. Глобальный `~/.config/opencode/cli.json`
подключает пакет из него; копии исходников в глобальном каталоге plugins не нужны.
Перед изменением конфигурации сохранить резервную копию, перечитать актуальный
файл и добавить запись ровно один раз. Существующие настройки и Orca сохраняются.
Документировать автоматическую перезагрузку конфигурации и `/reload`.

## Критерии приёмки

1. Все сценарии поведения панели и жизненного цикла покрыты соответствующими
   автоматическими проверками; проверки проекта проходят.
2. Чистый checkout устанавливается по lockfile и позволяет повторить проверки.
3. Собранный npm-tarball содержит только нужные файлы и загружается OpenCode.
4. В установленном OpenCode проверены секция, существующее дерево, изменение
   статуса и переход в сессию. Невыполненные интерактивные проверки перечислены
   отдельно; они не выдаются за успешные.
5. Репозиторий содержит пригодные для внешнего участника инструкции,
   лицензию, CI, правила совместимости и документированный выпуск версии.
6. Глобальное подключение работает рядом с существующим Orca-плагином.
